에이전트 하네스 구조 v3

자가진화 에이전트 개발용 템플릿. 지식 베이스 네 영역을 같은 라이프사이클로 축적하고, 모든 변경을 평가 게이트로 검증하며, 결과를 변경 레지스트리에 남긴다.

1. 전체 구조 — 세 개의 축

지식(무엇을 아는가) · 평가(얼마나 잘하는가) · 변경(무엇이 왜 바뀌었는가)이 서로를 참조한다.

Knowledge Base — knowledge/

Domain · Data · Learned · Dev 네 영역. 모든 지식 항목(Knowledge Item, KI)이 같은 형식과 라이프사이클을 따른다.

Eval Suite — evals/

Retrieval · Analysis · Regression 평가 세트와 베이스라인. KI와 이슈가 평가 케이스의 원천이다.

Change Registry — ops/

이슈, 변경 레코드, 실험. 변경 레코드 한 건 = 계기 → 가설 → 변경 내용 → 전후 점수 → 채택/롤백.

진화 대상 — agent/

프롬프트 · 스킬 · 도구 · 검색 설정. 성능에 영향을 주는 것은 전부 여기 있고, 평가 게이트를 통과한 변경만 반영된다.

문서 지도와 절차 — docs/ · .claude/ · ci/

기존 템플릿 그대로. SSOT → INDEX 문서 지도, 절차 스킬, CI 게이트.

2. 지식 흐름

원천 네 가지가 각 영역으로 Distill되고, 소비자는 둘이다. 대상 에이전트(만들어지는 제품)와 개발 에이전트 · 사람(만드는 쪽).

3. Knowledge Base 네 영역

사람의 암묵지는 넷 중 하나다. 개발 과정의 지식도 같은 무게로 축적한다.

영역담는 것원천KI 유형소비자
domain/사람이 하던 판단. "이 상황이면 이 데이터를 보고 이 기준으로 결론낸다"분석 케이스(문서 + raw data), 리포트, 인터뷰, 전문가 교정Decision Heuristic, Glossary, Exception Case대상 에이전트
data/방대한 DB에서 올바른 데이터를 찾는 법스키마, 성공 · 실패한 쿼리, RAG 검색 결과 분석Data Catalog, Query Pattern(목적 → 쿼리), Data Caveat(단위 · 중복 · 시점), Embedding/Chunking Note대상 에이전트
learned/에이전트가 실행 중 스스로 발견한 것트레이스, 자가 개선 제안Finding, Procedure Draft대상 에이전트 (Validate 후)
dev/에이전트를 만드는 과정에서 배운 것이슈, 변경 레코드, 기각된 실험, 평가 설계 경험Lessons Learned, Failure Mode, ADR, Rejected Experiment, Eval Design Note개발 에이전트 · 사람

4. 지식 라이프사이클

네 영역 모두 같은 여섯 단계를 거친다.

① Capture

원본을 raw/에 그대로 보관한다. 수정하지 않는다.

케이스, 스키마, 트레이스, 변경 레코드

② Distill

원본에서 KI 하나 = 사실 하나로 추출한다. 상태는 Draft.

스킬: distill-knowledge

③ Validate

KI를 Eval Case로 만들거나 Change Record의 점수로 뒷받침한다.

스킬: case-from-ki

④ Promote

근거가 붙으면 Validated. 영역 INDEX에 등록된다.

learned는 사람 승인 필요 (제안)

⑤ Serve

상황 태그로 검색해 필요한 KI만 제공한다. 사용 이력이 남는다.

런타임 / 개발 세션

⑥ Maintain

낡았거나 충돌하면 Re-validation. 진 쪽은 Deprecated로 바꾸고 대체 KI를 가리킨다.

스킬: review-knowledge

5. 적용 예시 — 분석 케이스로 지식 베이스를 처음 채우기 (Knowledge Bootstrapping)

raw data가 남아 있는 분석 케이스에서, 사람이 쓴 분석 문서와 데이터를 에이전트에게 주고 "어떻게 이렇게 분석됐는가"를 역분석시켜 지식으로 축적하는 흐름.

아래는 이해를 돕기 위한 가상의 케이스다.

단계에이전트가 하는 일남는 산출물
① Capture"주간 매출 급감 분석" 문서와 당시 데이터 스냅샷을 등록raw/cases/CASE-003/ (report, data, meta)
② Distill문서의 표 · 그래프(캡처 이미지)를 데이터와 대조. "채널별로 분해했고, 같은 요일 4주와 비교했고, 한 채널에 집중돼 채널 이슈로 결론" 을 재구성D-0007 Decision Heuristic, Q-0012 Query Pattern(채널별 주간 집계), DC-0004 Data Caveat(환불 건 제외 필요) — 모두 Draft
③ ValidateQ-0012로 조회해 문서의 수치가 재현되는지 확인. 설명되지 않는 부분은 전문가에게 질문 목록으로 전달재현 결과, 리뷰 기록, 전문가 답변(새 KI의 원천)
④ Promote재현되고 리뷰를 통과한 KI를 Validated로 승격KI 메타데이터의 evidence · last_verified 갱신, INDEX 등록
⑤ Blind 평가Hold-out 케이스(CASE-009 등)의 요청과 데이터만 받고 분석. 조회한 데이터와 결론을 사람의 문서와 비교Eval Case R-021(Retrieval), A-014(Analysis), 첫 Baseline
⑥ 불일치CASE-009에서 기간 조건을 잘못 잡아 오답 → 이슈 등록 → 변경 → 재평가ISS-0017 → CHG-0031 → L-0012 Lessons Learned

왜 Hold-out을 나누나

지식을 뽑은 케이스로 다시 평가하면 "외운 답"을 맞히는 것이다. 처음 보는 케이스로 평가해야 지식이 일반화되는지 알 수 있다.

왜 재현 검증인가

raw data가 있으므로 "문서의 수치가 다시 나오는가"로 Query Pattern을 객관적으로 검증할 수 있다. 추측한 분석 절차가 걸러진다.

data가 없는 옛 리포트는

재현할 수 없으므로 절차만 추출해 Draft로 둔다. 전문가 리뷰나 이후 유사 케이스의 평가 결과가 근거로 붙을 때 승격한다.

8. 관리 규칙

상태는 셋

Draft → Validated → Deprecated. Validated는 Eval Case, 재현 결과, Change Record 중 하나를 근거로 가져야 한다. Deprecated는 삭제하지 않고 대체 KI를 가리킨다.

KI 하나 = 사실 하나

100줄 이내. 영역마다 INDEX.md(60줄 이내)가 태그별 목록을 가진다. 넘치면 하위 영역으로 분할한다.

충돌은 평가로 결정

같은 상황에 상반된 KI가 생기면 둘 다 평가에 올려 진 쪽을 Deprecated 처리한다.

Re-validation

스키마가 바뀌면 관련 data KI를 재검증 대상으로 표시한다. 오래 검증되지 않은 KI는 정기 점검에서 다시 평가한다.

Promote 권한

에이전트는 Draft까지만 쓸 수 있다. Validated 승격은 평가 게이트 통과 + 사람 승인. (제안)

Rejected도 자산

기각된 실험은 dev/rejected로 남는다. "시도했지만 효과 없었다"가 없으면 같은 시도가 반복된다.

9. 변경 순환

사람의 변경이든 에이전트의 자가 개선 제안이든 같은 경로를 지난다.

Prior Knowledge

dev 영역에서 과거 시도 조회

Eval Case

변경 전에 케이스부터 등록

Change Candidate

가설 + agent/ 변경안

Eval Gate

전후 점수 · Regression 비교

Record · Distill

Change Record → dev KI 추출
