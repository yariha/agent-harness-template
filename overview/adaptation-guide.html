구조 수정 가이드 (Adaptation Guide)

에이전트 개발 시나리오가 달라질 때 템플릿 구조를 어디까지, 어떻게 바꾸는지 정한 문서. 템플릿에는 docs/adaptation/ 영역으로 들어갈 예정이다 (초안).

1. 먼저 구분할 것 — 바꾸면 안 되는 것과 바꿔도 되는 것

폴더 이름과 개수는 바꿔도 된다. 아래 여섯 가지 원칙이 깨지면 "나아졌는지 모르는" 상태로 돌아간다.

불변 원칙 (Invariants)

  • 변경에는 기록과 평가가 따른다. agent/를 바꾸면 Change Record와 전후 평가 결과가 있어야 한다.
  • 고치기 전에 Eval Case부터. 이슈는 먼저 평가 케이스로 등록한다.
  • 근거 없는 지식은 Draft. Validated는 평가, 재현, 변경 기록 중 하나를 근거로 가진다.
  • 원본 불변. raw/의 자료는 수정하지 않는다.
  • Hold-out은 추출에 쓰지 않는다. 평가용 케이스에서 지식을 뽑지 않는다.
  • 자가 개선도 같은 게이트. 에이전트의 제안도 사람의 변경과 같은 경로를 지난다.

조정 가능 (Adjustable)

  • Knowledge Base 영역의 수와 이름, 하위 분할
  • KI 유형 (Decision Heuristic, Query Pattern 등의 추가 · 삭제)
  • Eval Suite의 종류와 지표
  • 사람 승인이 필요한 지점과 자동화 수준
  • 저장 방식 (파일 → 검색 인덱스, 외부 LLMOps 도구)
  • agent/의 내부 구성 (단일 → 멀티 에이전트)

2. 수정 판단 순서

구조를 바꾸고 싶을 때 위에서부터 차례로 확인한다. 앞 단계에서 해결되면 멈춘다.

① 반복되는가

같은 불편이 2회 이상 관찰됐는가. 한 번이면 구조를 바꾸지 않는다.

② 기존 자리로 되는가

기존 폴더 · KI 유형 · 태그로 담을 수 있는가.

③ 유형 추가로 되는가

KI 유형이나 Eval Suite 하나를 추가하면 되는가.

④ 영역 추가

그래도 안 되면 새 영역 · 폴더를 만들고 INDEX와 SSOT Source Map에 연결한다.

⑤ 기록

구조 변경을 ADR로 남긴다. 무엇이 불편했고 왜 이렇게 바꿨는지.

3. 시나리오별 수정 방법

자주 만날 상황과 그때 바꿀 곳. 표시는 영향받는 축이다.

시나리오무엇이 달라지나어떻게 수정하나
raw data가 없는 리포트만 있다재현 검증(Replay)을 할 수 없다KnowledgeEval
절차만 추출해 Draft로 둔다. 평가는 수치 일치 대신 "어떤 데이터를 보고 어떤 기준으로 판단했나"를 채점 기준표로 본다. 전문가 리뷰 비중을 높이고, 새로 생기는 케이스부터 데이터 스냅샷을 함께 Capture한다.
케이스 수가 적다 (10건 안팎)Hold-out을 떼면 추출할 케이스가 부족하다Eval
한 건씩 번갈아 평가용으로 빼는 방식(leave-one-out)을 쓰거나, 기존 케이스는 모두 추출에 쓰고 이후 신규 케이스를 Hold-out으로 쌓는다. Baseline에 "표본 적음"을 표기해 점수를 과신하지 않는다.
정형 DB(SQL) 중심테이블 · 컬럼 선택과 조건이 정확도를 좌우한다KnowledgeEval
data/catalog/를 테이블 단위로 세분하고 Query Pattern을 강화한다. Retrieval 평가는 "쿼리 실행 결과가 정답과 같은가"로 채점한다. 스키마 변경을 감지해 관련 KI를 Re-validation 대상으로 표시한다.
RAG(임베딩 DB) 중심청킹 · 임베딩 · 검색 설정이 성능을 좌우한다AgentEval
인덱스 설정을 agent/retrieval/에 두고 Change Record 대상으로 삼는다. Eval Case에 "정답 문서 ID"를 넣어 검색 적중률을 따로 잰다. data/에 Chunking/Embedding Note 유형을 추가한다.
DB와 RAG를 함께 쓴다어느 쪽을 조회할지 고르는 판단이 추가된다KnowledgeEval
"이 목적이면 어느 소스"를 정리한 Routing Rule KI 유형을 추가한다. Retrieval Suite를 소스 선택 / 소스 내 조회 두 단계로 나눠 어디서 틀렸는지 구분한다.
멀티 에이전트에이전트마다 역할과 실패 지점이 다르다AgentEvalChange
agent/<name>/으로 분리한다. 평가는 에이전트별 + 전체 흐름(end-to-end) 두 층으로 둔다. Change Record에 대상 에이전트를 적는다. Knowledge Base는 공유를 기본으로 하고 전용 지식만 태그로 구분한다.
쓰기 작업을 하는 에이전트잘못된 실행이 실제 피해로 이어진다EvalGate
Safety Suite를 추가하고 평가는 격리 환경(sandbox)에서만 돌린다. 자가 개선의 자동 승격을 끄고, 되돌리기 어려운 동작은 사람 승인을 필수로 한다.
대화형 (여러 턴)한 번의 질문 · 답이 아니라 흐름을 평가해야 한다Eval
Eval Case를 대화 시나리오 단위로 만든다. 되묻기의 적절성, 맥락 유지 같은 대화 채점 기준을 추가한다.
정답이 주관적이다수치 일치로 채점할 수 없다Eval
채점 기준표(rubric)를 KI처럼 버전 관리하고, 판정 모델로 채점하되 사람이 표본을 주기적으로 검수해 판정 모델의 정확도를 확인한다. 채점 기준 변경도 Change Record 대상이다.
지식량이 급증한다 (KI 수백 건 이상)INDEX 파일만으로 찾기 어렵다Knowledge
영역을 하위로 분할하고, KI 메타데이터를 그대로 쓰는 검색 인덱스를 추가한다. 파일이 원본, 인덱스는 파생물로 둔다. review-knowledge 주기를 짧게 한다.
도메인이 여러 개다도메인마다 판단 기준과 데이터가 다르다KnowledgeEval
knowledge/domain/<sub>/와 도메인별 Eval Suite로 나눈다. 공통 지식은 상위에 남긴다. 한 도메인의 변경이 다른 도메인을 깨는지 Regression으로 확인한다.
평가 비용 · 시간이 크다변경마다 전체 평가를 돌리기 어렵다EvalGate
빠른 세트(smoke)와 전체 세트(full)로 나눈다. 변경마다 smoke, 채택 직전과 정기적으로 full을 돌린다. Change Record에 어느 세트로 평가했는지 적는다.
기반 모델을 교체한다모든 점수의 기준이 바뀐다ChangeEval
모델 교체 자체를 Change Record로 남기고 전체 평가 후 Baseline을 다시 잡는다. 이전 모델용으로 넣은 보정 지식 · 규칙이 아직 필요한지 prune-harness로 점검한다.
외부 LLMOps 도구를 도입한다트레이스 · 평가 결과가 도구로 옮겨간다Change
traces/와 evals/results/를 도구로 옮기되 Change Record 번호를 실행 태그로 붙여 연결을 유지한다. Change Registry와 Knowledge Base는 저장소에 남긴다.
팀이 커진다동시에 여러 변경이 진행된다ChangeGate
변경 하나에 가설 하나 원칙을 강제한다. 여러 변경을 한꺼번에 평가하면 무엇이 효과였는지 알 수 없다. KI와 Eval Case에 담당자를 적는다.

4. 자가진화 자동화 수준

처음에는 낮은 단계에서 시작하고, 조건을 충족할 때 한 단계씩 올린다.

단계에이전트가 할 수 있는 것올리는 조건
L0 수동사람만 지식과 agent/를 바꾼다시작점. Eval Suite와 Baseline이 생기기 전
L1 제안에이전트가 자가 개선 제안을 Draft로 쌓는다. 반영은 사람이 한다Baseline 확정, Regression Suite 존재
L2 조건부 사용Draft 지식을 실험 실행에서만 써 보고 결과를 제안에 첨부한다제안의 채택률이 안정적, 격리 실행 환경 존재
L3 저위험 자동 승격Eval Gate를 통과한 저위험 유형(예: Data Caveat 추가)은 자동 Promote, 사후 검토자동 승격분의 롤백 이력이 낮음, 유형별 위험 분류 합의

내릴 때

자동 승격된 지식이 Regression을 일으키면 해당 유형을 한 단계 내리고, 원인을 Failure Mode로 기록한다.

5. 피해야 할 수정

급해서 게이트를 건너뛴다

"이번만" 기록 없이 고치면 그 변경이 이후 모든 점수 변화의 원인 불명 요소가 된다. 급한 수정도 Change Record는 사후에라도 남긴다.

Eval Case를 고쳐서 통과시킨다

점수가 떨어졌을 때 문제를 바꾸면 Baseline의 의미가 사라진다. Eval Case 수정도 Change Record 대상이다.

영역을 미리 만든다

쓰일지 모르는 폴더와 유형을 미리 만들면 빈 구조가 지도만 복잡하게 한다. 필요가 2회 확인된 뒤에 만든다.

긴 문서로 되돌아간다

KI를 합쳐 긴 문서 하나로 만들면 개별 검증 · 폐기 · 추적이 불가능해진다. 길어지면 합치지 말고 나눈다.

6. 구조를 바꾼 뒤 할 일

  • 변경 이유와 대안을 knowledge/dev/decisions/에 ADR로 남긴다.
  • docs/SSOT.md의 Source Map과 관련 INDEX를 갱신한다 (maintain-highway).
  • CI의 Eval Gate가 새 폴더 · 새 Suite를 인식하는지 확인한다.
  • 불변 원칙 여섯 가지가 여전히 지켜지는지 점검한다.
