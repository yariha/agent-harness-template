# Adaptation Scenarios

> 자주 만나는 상황과 그때 바꿀 곳. 적용 전에 [INDEX.md](./INDEX.md)의 수정 판단 순서를 먼저 확인한다.

## 데이터·케이스 조건
| 시나리오 | 무엇이 달라지나 | 어떻게 수정하나 |
| --- | --- | --- |
| raw data가 없는 리포트만 있다 | Replay를 할 수 없다 | 절차만 추출해 Draft로 둔다. 평가는 수치 일치 대신 "어떤 데이터를 보고 어떤 기준으로 판단했나"를 채점 기준표로 본다. 전문가 리뷰 비중을 높이고, 새로 생기는 케이스부터 데이터 스냅샷을 함께 Capture한다. |
| 케이스 수가 적다 (10건 안팎) | Hold-out을 떼면 추출할 케이스가 부족하다 | 한 건씩 번갈아 평가용으로 빼는 방식(leave-one-out)을 쓰거나, 기존 케이스는 모두 추출에 쓰고 이후 신규 케이스를 Hold-out으로 쌓는다. `evals/baseline.json`의 `notes`에 표본이 적음을 적는다. |
| 정답이 주관적이다 | 수치 일치로 채점할 수 없다 | 채점 기준표(rubric)를 `evals/` 아래에서 버전 관리하고 판정 모델로 채점한다. 사람이 표본을 주기적으로 검수해 판정 모델의 정확도를 확인한다. 채점 기준 변경도 Change Record 대상이다. |

## 데이터 소스
| 시나리오 | 무엇이 달라지나 | 어떻게 수정하나 |
| --- | --- | --- |
| 정형 DB(SQL) 중심 | 테이블·컬럼 선택과 조건이 정확도를 좌우한다 | `knowledge/data/catalog/`를 테이블 단위로 세분하고 Query Pattern을 강화한다. Retrieval 평가는 쿼리 실행 결과가 정답과 같은지로 채점한다. 스키마 변경 시 관련 KI를 Re-validation 대상으로 표시한다. 에이전트 계정은 read-only로 둔다. |
| RAG(임베딩 DB) 중심 | 청킹·임베딩·검색 설정이 성능을 좌우한다 | 인덱스 설정을 `agent/retrieval/`에 두고 Change Record 대상으로 삼는다. Eval Case의 `expected`에 정답 문서 ID를 넣어 검색 적중률을 따로 잰다. `knowledge/data/`에 Chunking/Embedding Note 유형을 추가한다. |
| DB와 RAG를 함께 쓴다 | 어느 쪽을 조회할지 고르는 판단이 추가된다 | "이 목적이면 어느 소스"를 정리한 Routing Rule KI 유형을 추가한다. Retrieval Suite를 소스 선택 / 소스 내 조회 두 단계로 나눠 어디서 틀렸는지 구분한다. |
| 도메인이 여러 개다 | 도메인마다 판단 기준과 데이터가 다르다 | `knowledge/domain/<sub>/`와 도메인별 Eval Suite로 나눈다. 공통 지식은 상위에 남긴다. 한 도메인의 변경이 다른 도메인을 깨는지 Regression으로 확인한다. |
| 지식량이 급증한다 (KI 수백 건 이상) | INDEX 파일만으로 찾기 어렵다 | 영역을 하위로 분할하고, KI frontmatter를 그대로 쓰는 검색 인덱스를 추가한다. 파일이 원본, 인덱스는 파생물이다. `review-knowledge` 주기를 짧게 한다. |

## 에이전트 형태
| 시나리오 | 무엇이 달라지나 | 어떻게 수정하나 |
| --- | --- | --- |
| 멀티 에이전트 | 에이전트마다 역할과 실패 지점이 다르다 | `agent/<name>/`으로 분리한다. 평가는 에이전트별 + 전체 흐름(end-to-end) 두 층으로 둔다. Change Record `targets`에 대상 에이전트가 드러나게 한다. Knowledge Base는 공유를 기본으로 하고 전용 지식만 태그로 구분한다. |
| 쓰기 작업을 하는 에이전트 | 잘못된 실행이 실제 피해로 이어진다 | Safety Suite를 추가하고 평가는 격리 환경에서만 돌린다. 자동화 수준을 L1 이하로 고정하고, 되돌리기 어려운 동작은 SSOT의 허락 필수 변경에 넣는다. |
| 대화형 (여러 턴) | 한 번의 질문·답이 아니라 흐름을 평가해야 한다 | Eval Case의 `input`을 대화 시나리오 단위로 만든다. 되묻기의 적절성, 맥락 유지 같은 대화 채점 기준을 추가한다. |

## 운영 조건
| 시나리오 | 무엇이 달라지나 | 어떻게 수정하나 |
| --- | --- | --- |
| 평가 비용·시간이 크다 | 변경마다 전체 평가를 돌리기 어렵다 | 빠른 세트(smoke)와 전체 세트(full)로 나눈다. 변경마다 smoke, 채택 직전과 정기적으로 full을 돌린다. Change Record의 `eval_suite`에 어느 세트였는지 적는다. |
| 기반 모델을 교체한다 | 모든 점수의 기준이 바뀐다 | 모델 교체 자체를 Change Record로 남기고 전체 평가 후 Baseline을 다시 잡는다. 이전 모델용 보정 지식·규칙이 아직 필요한지 `prune-harness`로 점검한다. |
| 외부 LLMOps 도구를 도입한다 | 트레이스를 도구에서도 본다 | 기본 경로는 Langfuse(`observability/LANGFUSE.md`): 원본은 `traces/`에 두고 OTLP로 사본을 보낸다. 다른 도구도 OTLP를 받으면 `lib/otlp.mjs`를 그대로 쓴다. Change Record ID를 실행 태그로 붙여 연결을 유지한다. Change Registry와 Knowledge Base는 저장소에 남긴다. |
| LLMOps 도구를 쓰지 않는다 | 없음 | Langfuse 키를 비워 둔다. 기록·뷰어·비용 내역은 로컬만으로 동작한다. |
| 팀이 커진다 | 동시에 여러 변경이 진행된다 | 변경 하나에 가설 하나 원칙을 강제한다. KI와 Eval Case에 담당자 필드를 추가한다. Change Record ID 충돌을 막기 위해 번호를 브랜치 병합 시점에 확정한다. |

## 여기 없는 상황이면
수정 판단 순서를 따르고, 정한 내용을 ADR로 남긴 뒤 이 표에 한 행을 추가한다. 같은 상황이 두 번째로 오면 그 행이 가이드가 된다.
